# 2026-10-01 Frontend Changelog

## ⚠️ Breaking Changes

### 臨打團新增「報名截止時間」

建立臨打團時，`POST /pickup-groups` 現在**必填** `registration_deadline`，格式為 RFC 3339，例如：

```json
{
  "registration_deadline": "2026-10-02T18:00:00+08:00"
}
```

`registration_deadline` 不得晚於 `start_time`，建立或修改時也不得為過去時間；修改 `start_time` 時同樣會重新驗證。驗證失敗回傳 `400`。到達截止時間後，單人／多人報名以及恢復已取消的報名皆會回傳 `400`。

`PATCH /pickup-groups/{id}` 可選填 `registration_deadline`，省略時保留原值。臨打團列表、詳細資料，以及訂單中的臨打團摘要現在都會回傳 `registration_deadline`。

### 報名不再從 request 傳入自己的程度

`POST /pickup-groups/{id}/orders` 的單人報名現在**不需要 body**。使用者本人的程度會直接讀取帳號中該運動的自評程度；舊版前端即使傳入 `skill_level` 也會被忽略。

若使用者尚未設定該運動的自評程度，報名會回傳 `400`，因此前端應在報名前確認是否已完成設定。

多人報名時，`members[0]` 仍代表本人，其 `skill_level` 可以省略並由帳號設定覆蓋；匿名同行者仍必須提供 `skill_level`。

## 帳號自評程度

新增使用者自己的運動程度設定 API。此設定與 `/me/skill-ratings` 的團主評分是不同資料，前端顯示時不要混用。

- `GET /me/skill-levels`：取得所有已設定的運動程度，回傳 `{ items, page, page_size, total }`。
- `GET /me/skill-levels/{sport_id}`：取得指定運動的程度；尚未設定時回傳 `400`。
- `PUT /me/skill-levels/{sport_id}`：建立或更新程度，body 為 `{ "skill_level": 2 }`。
- `DELETE /me/skill-levels/{sport_id}`：清除程度，成功回傳 `204`。

`skill_level` 必須是該運動目前有效的 `1–100` 整數。

## 臨打團建立權限調整

現在所有**已登入且帳號啟用的使用者**都可以建立臨打團，不再需要 `is_pickup_host`。

如果前端原本使用 `is_pickup_host` 控制「建立臨打團」按鈕或頁面權限，應移除此限制。建立者仍可編輯自己的團、查看與審核自己的報名，以及使用既有團主功能。

`is_pickup_host` 欄位仍存在，但只用於既有教練清單與追蹤功能，不應再拿來判斷是否能建立臨打團。

## 臨打團與報名行為調整

### 訂單查看權限

以下 API 現在僅限團主本人或系統管理員使用，其他使用者回傳 `403`：

- `GET /pickup-groups/{id}/orders`
- `GET /pickup-groups/{id}?include_orders=true`

前端如果一般使用者頁面原本會帶 `include_orders=true`，需要移除或依權限判斷。

### 報名驗證調整

單人／多人報名，以及恢復已取消的訂單時，會重新檢查團狀態、剩餘名額與時段衝突。

停用、已取消、已完成、已結束或已超過報名截止時間的團無法報名，通常回傳 `400`；名額不足、重複報名或時段衝突則回傳 `409`。

已取消的臨打團不再被視為時段衝突來源。

### 修改臨打團

`PATCH /pickup-groups/{id}` 有以下新增限制：

- 已有任何報名或評分紀錄後，不可修改 `sport_id`，回傳 `409`。
- 縮減容量時，如果新容量低於目前報名人數，回傳 `409`。
- 修改時段或重新啟用時，如果造成參加者與其他臨打團時段衝突，回傳 `409`。
- 驗證失敗時整次修改不會套用。

### 取消報名

`PATCH /pickup-orders/{id}`：對於已確認、已付款或已申請取消的訂單，報名者不能直接將狀態改為 `cancelled`，否則回傳 `403`。

這類訂單需走 `cancel_request` 流程，由團主或系統管理員處理。前端應避免在這些狀態下直接提供「立即取消」操作。

### 刪除臨打團

`DELETE /pickup-groups/{id}`：如果該團已有訂單或評分紀錄，會回傳 `409`。

## 組織、場館與預約

組織停用後，一般使用者仍可讀取歷史資料，但不能再修改組織、場館、資源、封面、成員或管理員，也不能新增、修改或刪除預約，相關操作會回傳 `403`。

另外有以下行為調整：

- 指派組織管理員或場館管理員時，如果角色衝突會回傳 `409`。
- 指派組織管理員時，如果對方尚未加入組織會回傳 `400`。
- 組織管理員修改自己的預約時，也會套用管理員權限。
- 刪除仍有相關預約的資源或場館時會回傳 `409`。

前端應針對上述 `400`、`403`、`409` 情境提供適當錯誤提示。

## 個人資料與清單行為

使用者清單的 `sort_by=name` 現在會正確依 `display_name` 排序。

分頁查詢超過最後一頁時，API 會回傳空的 `items`，但 `total` 仍是符合條件的實際總數。因此前端不要以 `items.length === 0` 推斷 `total === 0`。

## 系統管理員手動通知

新增：

```http
POST /notifications
```

僅系統管理員可使用。Request：

```json
{
  "user_ids": ["使用者 UUID"],
  "title": "通知標題",
  "content": "通知內容"
}
```

`user_ids` 可指定 1–100 位使用者；`title` 為 1–100 字，`content` 為 1–2000 字。通知內容是**純文字**，前端應以純文字方式呈現，不要當作 HTML render。

成功回傳：

```json
{
  "sent": 1
}
```

可能的錯誤包含：無效內容或收件者回傳 `400`、未登入回傳 `401`、非系統管理員回傳 `403`、超過發送限制回傳 `429`。

通知清單的 `type` 新增：

```text
admin_message
```

前端通知元件需要支援此類型。

## 使用者 LINE ID

`POST /auth/register`、`PATCH /me`、`PATCH /users/{id}` 新增選填欄位 `line_id`。

非空值格式必須符合：

```regex
^[a-z0-9._-]{4,20}$
```

也就是 4–20 個小寫英文字母、數字、`.`、`-` 或 `_`。格式不符回傳 `400`。

PATCH 時：

- `"line_id": ""`：清除 LINE ID。
- 省略 `line_id`：保持原值。
- `"line_id": null`：保持原值。

註冊時傳空字串則視為未設定。

使用者 response 現在會新增：

```json
{
  "line_id": null
}
```

此欄位只有使用者本人與系統管理員可見。
