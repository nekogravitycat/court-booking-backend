# 2026-10-03 Frontend Changelog

## ⚠️ Breaking Changes

### 400 錯誤回應不再包含 `details`

所有 `400` 回應現在一律為統一的格式，只有 `error` 一個欄位：

```json
{
  "error": "invalid request body"
}
```

先前參數、body 或 query 綁定失敗時，回應還會多帶 `details`（框架驗證器的原始錯誤字串，例如欄位名稱與驗證規則）。該欄位已移除，OpenAPI 的 `ErrorResponse` 也一併拿掉。

- 前端若有讀取 `details` 來顯示或記錄，請改用 `error`。
- `error` 的值依失敗位置固定為以下三種之一：
  - 路徑參數錯誤（例如 ID 不是 UUID）：`invalid request`
  - JSON body 錯誤：`invalid request body`
  - Query string 錯誤：`invalid query parameters`
- 業務驗證失敗的 `400`（例如 `display_name must not be blank`、`invalid sport_id`）訊息不變。

## 回應調整

### `DELETE /pickup-groups/{id}` 成功回應

成功時回傳 `204 No Content`，且**沒有 body**。先前回傳的 `204` 帶有 `null` 的 body，這在 HTTP 上不合法，部分客戶端 / fetch 封裝可能因此解析失敗。

前端若對 `204` 回應無條件呼叫 `response.json()`，請改為略過；其他刪除 API 本來就是這個行為。

### 場地管理相關的 `403` 訊息

權限本身沒有變，只是訊息對齊實際行為（組織管理員同樣有權限）：

| API | 新訊息 |
| --- | --- |
| `POST /locations` | `forbidden: only organization owners or managers can create locations` |
| 指派場地管理員 | `forbidden: only organization owners or managers can assign location managers` |
| 移除場地管理員 | `forbidden: only organization owners or managers can remove location managers` |

若前端依賴訊息字串做判斷或顯示，請更新；建議改以 HTTP 狀態碼 `403` 判斷。

### 查詢使用者權限失敗時的行為

部分 API 以前在後端查不到使用者資料時，會靜默視為「不是管理者」而回 `403`。現在這類錯誤會原樣回報：

- 認證層（所有需登入的 API）查詢帳號失敗：維持 `401`（`account is inactive or no longer exists`）。
- `GET /bookings/{id}` 在判斷組織管理權限時發生資料庫錯誤：回 `500`，不再回 `403`。

正常情況下（帳號存在且啟用）不受影響。

## 無需前端處理的內部調整

以下項目沒有改變 request / response 格式或權限規則，列出僅供參考：

- 場地、組織、資源、預約等列表的分頁、排序與總數計算行為不變；第 1 頁沒有任何資料時，`total` 為 `0`。
- 組織封面與使用者頭像的更換 / 移除改為單一原子操作，連續快速更換時不再有舊檔案殘留的情況；API 不變。
- 圖片上傳（`ResizeImage`）改為只解碼一次，主檔與縮圖產生結果與先前一致。
- `GET /bookings/{id}`、`GET /pickup-groups/{id}/orders` 等 API 的權限判斷集中到後端服務層，可見性規則不變。
- `GET /resources/{id}/availability` 改用更輕量的查詢，回傳內容不變。
